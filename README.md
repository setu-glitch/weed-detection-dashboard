# AI-Powered Precision Weed Management

A research dashboard for AI-assisted weed detection in soybean cultivation,
built around an open-source FarmBot platform. Developed as a research prototype
at the Technical University of Munich.

The dashboard runs the perception stage of an autonomous weeding pipeline: an
image of a soybean bed goes in, and a labelled map of crop and weed instances
comes out, together with the statistics an intervention decision needs.

## What it does

| Section | Purpose |
| --- | --- |
| Overview | Pipeline at a glance, model availability, study findings |
| Live monitoring | Stored camera frame with on-demand analysis; ready for a live feed |
| Weed detection | Upload an image, pick a model, get annotated results and statistics |
| Autonomous weeding | Weed targets and intervention decision; actuator stage inactive |
| Model information | The five YOLO generations compared, with published accuracy figures |
| Dataset | Capture, annotation and class configuration read from `data.yaml` |
| About | Research context and how the numbers in the interface are sourced |

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate

# Install CPU-only PyTorch first to avoid pulling ~2 GB of CUDA wheels.
pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt

# Add the trained checkpoints
cp /path/to/weights/*.pt models/

streamlit run app.py
```

The app opens at <http://localhost:8501>.

It starts without checkpoints too: missing models are reported as "not
installed" and every other page keeps working, which is useful for reviewing
the interface before the weights are in place.

## Configuration

**Models.** `utils/config.py` holds `MODEL_REGISTRY`. Each entry names a
checkpoint file expected in `models/`. Adding a model means adding one
`ModelSpec` and dropping the file in — no UI code changes.

```python
ModelSpec(
    key="yolov13n",
    label="YOLOv13n",
    filename="yolov13n.pt",
    generation="v13",
    released="2026",
    architecture="…",
)
```

**Classes.** Class names come from `data.yaml`, the same file used for training.
Replace the template in the project root with your Roboflow export. Which class
names count as weeds is decided by the keyword lists in `utils/config.py`
(`WEED_KEYWORDS`, `CROP_KEYWORDS`); an unrecognised name is treated as crop so a
typo can never inflate the weed count that drives intervention.

**Published results.** `benchmarks.json` holds the accuracy figures from the
training study. Values left as `null` render as a dash — the dashboard never
invents a number to fill a gap. Add your own measured precision, recall and mAP
values there as they are transcribed from the experiments.

**Paths.** `WEED_MODELS_DIR`, `WEED_ASSETS_DIR`, `WEED_DATA_YAML` and
`WEED_BENCHMARKS` override the default locations, which helps when weights live
on a mounted volume.

**Monitoring frame.** `assets/dummy_monitoring.jpg` is a synthetic stand-in
generated by `assets/generate_placeholder.py`. Replace it with a real capture
from the FarmBot camera position; detection results on a synthetic image mean
nothing.

## Project structure

```
weed_detection_dashboard/
├── app.py                  UI composition and page routing
├── requirements.txt        CPU-only torch pinning
├── packages.txt            System libraries for hosted builds
├── Dockerfile              Container image for Cloud Run and VMs
├── DEPLOYMENT.md           Platform-by-platform deployment guide
├── data.yaml               Dataset classes (replace with your export)
├── benchmarks.json         Published study results
├── .streamlit/config.toml  Theme and upload limits
├── models/                 YOLO checkpoints (.pt)
├── assets/
│   ├── dummy_monitoring.jpg
│   └── generate_placeholder.py
└── utils/
    ├── config.py           Paths, model registry, class mapping, palette
    ├── dataset.py          data.yaml parsing and class resolution
    ├── model_manager.py    Discovery and lazy cached loading
    ├── detection.py        Inference and derived statistics
    ├── visualization.py    Bounding-box rendering and density overlay
    ├── farmbot.py          Actuator boundary and target planning
    └── ui.py               Stylesheet and HTML components
```

`detection.py`, `visualization.py` and `farmbot.py` do not import Streamlit, so
the same pipeline can drive a batch script or the future control loop.

## Performance on modest hardware

- Checkpoints load on first use and stay cached, so only the models you actually
  run occupy memory. Five models are never resident at once.
- Inference is pinned to CPU; no GPU is assumed anywhere.
- Uploads larger than 1600 px on the long edge are downscaled before inference,
  and the interface says so when it happens.
- Uploads are capped at 20 MB in `.streamlit/config.toml`.
- Rendering uses Pillow rather than OpenCV, which keeps the image stack small.

Expect roughly 0.3–1.5 s per image for a nano model at 640 px on a shared
free-tier vCPU. Dropping the inference resolution to 416 px in the detection
settings roughly halves that.

## Deployment

See [DEPLOYMENT.md](DEPLOYMENT.md) for step-by-step instructions. In short:
Streamlit Community Cloud is the easiest free option, Google Cloud Run if you
prefer the included `Dockerfile`, Oracle Cloud Always Free if you want a real
VM. Hugging Face Spaces is no longer free for apps that run on compute.

Two files exist for the hosted case: `requirements.txt` pins the CPU-only torch
index so builds do not pull the CUDA wheels, and `packages.txt` installs the
system libraries OpenCV needs on slim Debian images.

## How the numbers are sourced

Two kinds of numbers appear in this dashboard and are never mixed:

- **Measured.** Detection counts, confidences and inference times come from the
  model run you trigger, computed from the actual output.
- **Published.** Accuracy figures such as mAP@0.5 come from `benchmarks.json`
  and are labelled as study results wherever they appear.

The autonomous weeding page plans targets from real detections but sends
nothing. `utils/farmbot.py` raises `FarmBotNotConnected` for every actuator
command until a real client is installed, so the interface cannot suggest that
physical weeding took place.

## Extending it

Each planned capability has a seam already in place:

| Next step | Where |
| --- | --- |
| Live camera feed | Replace `load_monitoring_frame()` in `app.py` |
| FarmBot control | Implement `FarmBotClient`, register it with `set_client()` |
| Pixel → bed coordinates | Extend `WeedTarget` with the camera calibration |
| Detection history | Persist `DetectionResult` objects; they are plain dataclasses |
| Field density maps | Generalise `density_overlay()` to georeferenced captures |
